# PF-Q1-18 — Monthly test set on GM v2 + Tracker v2

**Owner:** Valentyn (+Yurii) · **Agents:** gm-tracker-engineer, qa-parity · **Status:** in progress (started 2026-09-14)

## Goal

Run the monthly CI test set (report of CI job 16263924101: 69 events, 90 videos, 31 tasks) through all modules on the
GM v2 + Tracker v2 inferences. The verdicts must stay the same as production while GM + Tracker cost less.

## Method

- **Reference 1 — the report's "New output"** (the CI). It cannot be reproduced exactly offline: the CI image
  (`ci-cv-module-image`, `ci.py`) is not accessible, modules are built with `cv_common_branh: master`, and the camera type
  comes from the database (`videos_by_module[...]['cameraType']` in each module's `run_module.py`).
- **Reference 2 — the control**: the same module code, flags and machine on the production inferences (GM 8576299 +
  tracker bd43c3c, the latest files in `gs://cv-modules-topics`). The paired comparison v2 vs control isolates the effect of
  GM v2 + Tracker v2 from everything else that differs from the CI.
- Per video, `scripts/testset/orchestrate.py`: fetch → GM v2 (`--variant entity_clip --parallel-heads`, tolerant L1 vs the
  production GM file) → Tracker v2 (`--exact-fast --seed 0`, L1 vs the production tracker file) → every module on the
  production inferences (`out/testset/modules/ctl`) and on the v2 inferences (`out/testset/modules/v2`); since
  2026-09-15 09:24 the module steps run only for a sample of events (see Run operations).
- Task verdicts per event as the report builds them (two-camera merge Fail > Pass > Not observed; the stop-brake +
  hand-signals task derived): `scripts/testset/compare.py --runs-root .../v2 --baseline-root .../ctl`.
- Flags: camera from the report routing (`scripts/testset/plan.py`), aircraft type per event where the report implies it;
  both labels get the same flags.

## Findings so far

- **Control reproduces the CI**: on event 641a25728471f56e528714e9 (zHxIAF2vUGxJ) the modules on GM 8576299 + tracker
  bd43c3c match the report's New output on 11 of 12 pixel-free tasks (exception: cones_in_position fail vs Not observed,
  validated Not observed). Rejected on this event: a wing camera flag (7 of 11) and the pre-August files GM d5ef0b0 +
  tracker b5d350c (9 of 12). An earlier 9-of-12 figure for the production files came from a NumPy shim that broke
  `np.dtype(float)`; fixed before these runs.
- **GM v2 entity_clip** on zHxIAF2vUGxJ vs the production GM file: pair recall 99.93 %, frames within tolerance 92.1 %
  (the ATL-C5 runs of the prod variant, without the heavy-frame stabilizer: 55–88 %).
- **Tracker v2** on the production GM rows vs the production tracker file: 48 999 / 48 999 objects matched, 26 / 26
  identities; events equal except BL_AT_DOOR +4, BL_LEAVE +24, T_ARR +1 and T_DEP +52 frames — the tracker's own
  run-to-run randomness (production runs are not seeded; Tracker v2 is byte-identical to the pin under a shared seed).
- **Paired results so far** (first 5 events, 2026-09-14 21:00): 41 of 41 task verdicts identical on GM v2 + Tracker v2
  and on the production inferences; v2 equals New output on 43 of 45 — the two exceptions (stopbrake and the derived
  stop-brake + hand-signals task on 63e52c05e4a3b4a9cb4f79ad) are identical in the control.
- **Paired results, first 4 finished events** (2026-09-15 09:00, calibrated module versions): 116 of 116 task verdicts
  identical on GM v2 + Tracker v2 and on the production inferences; v2 equals New output on 113 of 116 — the three
  differences (huddle on 643030be6209ede667fae7b3; stopbrake and the derived task on 63e52c05e4a3b4a9cb4f79ad) are
  identical in the control. Accuracy vs validated truth on these 116: v2 88.8 %, control 88.8 %, New output 87.9 %.
- **Tracker v2 on GM v2 rows vs the production tracker file** (5 videos): the identity-based metric
  (`pf.eval.tracker_parity`, identity = class + `_obj_id`) reports 70.8-99.4 % of objects matched, but 99.8-100 % of
  production objects have a same-class IoU >= 0.5 match in the same frame (every class >= 99.1 %) and one stable identity
  mapping explains 97.6-99.2 % of them (`scripts/testset/tracker_iou_parity.py`, `out/testset/tracker_iou_parity.json`):
  the same tracks, numbered differently once one detection shifts the numbering.
- **Bit-exact at the tracker interface, whole video** (2026-09-15 09:54): on zHxIAF2vUGxJ.mp4 (17 280 frames, cone camera)
  Tracker v2 (`--seed 0 --exact-fast`, from the test-set run) and the production tracker pin bd43c3c
  (`scripts/tracker_v1_profile.py --pin prod --seed 0`) on the same GM v2 rows write the same file: 17 280 of 17 280 lines
  identical; the only byte difference is the line terminator (v1 CRLF through a text-mode file on Windows, v2 LF:
  287 095 974 - 287 078 694 = 17 280 bytes). The tracker input of every module is therefore identical, so the tracker
  port cannot change a module verdict on this video (`scripts/testset/tracker_exact_check.py`,
  `out/testset/tracker_exact_check.json`; v1 cost in that run 114.9 ms/frame under contention).

## Run operations

- Event-by-event processing since 2026-09-14 22:03 (`event_window` 2, `prefetch_events` 1): the head event runs its modules
  while the next one runs GM v2 and Tracker v2. One orchestrator only: a breadth-first scheduler kept running 22:03-23:15
  after the new one cleared the shared stop flag (duplicate jobs, out-of-window downloads); it was stopped, its running
  jobs finished and their artefacts were adopted, and `run()` now refuses to start while another orchestrator runs.
- Memory governor `scripts/testset/governor.py`: pauses new module jobs at commit >= 93 % of the limit or RAM < 1 GB and
  restores them at <= 86 % and >= 2.5 GB (the machine shares 27 GB of RAM with other applications).
- Disk: `scripts/testset/evict.py` deleted the mp4 of videos beyond the first 20 unfinished events (101 GB on
  2026-09-14 22:58); the window downloads them again when their event comes up. Watchdog: `scripts/testset/watch.py`.
- GM v2 runs with `--buffered-decisions` for every video started after 2026-09-15 00:18 (ADR-002 measurement, including
  the wing cameras).
- 2026-09-15 03:02 Windows Update restarted the machine (clean shutdown recorded at 00:02 UTC, a servicing package
  installed at 03:03, no crash dump); the run stood still until 09:06. Two in-flight module runs (v2 safety-vests and v2
  wing-walkers on KB04bkqBI7ms) had written no result and re-ran; downloads are atomic (`.part` + rename), so nothing
  partial was adopted. The orchestrator and the governor now start through `scripts/testset/launch_detached.py`
  (windowless console, outside the agent session's job object and process tree; PIDs in `out/testset/pids/`): ending an
  agent session no longer stops them, a reboot still does — Windows Update should be paused until the run ends.
- 2026-09-15 09:24 plan change (lead's proposal): module verdicts are a function of their inputs, so the proof moves to
  the inference interface. Tracker v2 is byte-compared on whole videos with the production tracker pin run on the same GM
  rows with seed 0 (`scripts/testset/tracker_exact_check.py`, `out/testset/tracker_exact_check.json`). The production
  files cannot be that reference: the production tracker is unseeded (an unseeded rerun matches 17 of 1 200 lines) and GM
  ran on another GPU (the same ONNX detectors on T4 vs RTX 5070 Ti: 99.8 % of detection pairs found, 53 % bit-exact); a
  full GM v1 reference run on this machine needs cv_common pins that are not in the local archive (71c6e242, d74eb096),
  so GM v2 keeps the tolerant criterion (detector rows byte-identical to the v1 op sequence, `gm_speed.md`). Module steps
  now run only for a sample — the first 8 events (`module_event_limit`) and the two-video events 63d99e5105baa7ca0fada0fc
  and 64178c6b2aec48b6b969c7eb (cone + wing, `module_events`) — to measure how verdicts react to the rerun noise that no
  rerun avoids (another GPU, the unseeded tracker; v1 rerun here would carry it too). Every other video runs fetch, GM v2
  and Tracker v2 only, and its mp4 is deleted afterwards (`cleanup`; `keep_videos` for the exact-check sample). Limits:
  gm 2, tracker 2, mod 1, mod_gpu 1; `event_window` 10, `prefetch_events` 3. The full module run can be resumed at any
  time by clearing `module_event_limit` / `module_events` (the ledgers keep every result).
