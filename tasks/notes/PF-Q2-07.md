## Why

The client's strongest interest is real time: a notification about what is going wrong at the gate while it can still be
corrected there. The product is therefore an **actionable alert** — the right violation, seconds after the client rule is
met, to the person who can fix it — and a record of whether it was fixed. A verdict that only arrives earlier is not enough.

## Success measures, per alert type

| measure | definition | target (proposal, fixed in PF-Q2-08) |
|---|---|---|
| time to alert | from the frame where the client rule is met to the notification | ≤ 10 s p95 (the RT prototype adds ≈2–4 s of chunking and processing) |
| false alerts | alerts without a labelled violation, per event | ≤ 1 per 20 events per alert type |
| recall | labelled violations that raised an alert | not lower than the batch module's Fail recall on the same labels |
| fixed on site | alerts resolved (the module sees the fix) before the stage ends | measured, no target in the MVP |

## Alert record (input for the ADR in PF-Q3-01)

`schema_version`, alert id, session / event id, gate, camera, alert type and check, object (track id and class), state
(`raised` → `updated` → `resolved` | `expired`), `provisional` (the module's verdict can still change), frame where the
rule was met, first and last frame of the violation, capture and emission times, severity, evidence (frame ids or a clip),
module and model versions. Source: the RT runtime's outputs (`kind`, `name`, `frame_id`, `payload`, `emitted_t`); hooks
emit `alert` when the rule is met and `resolved` when the fix is seen.
