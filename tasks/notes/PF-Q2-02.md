## Scope

The scope is fixed by the real-time module list v1: 22 modules, in groups A, B and C.

- **GM:**
  - all 26 decision classes and all three heads (main, chock, vehicle), because the RT modules read every class;
  - camera, aircraft-type and entity decisions go to the context component (PF-Q2-14).
- **Tracker:**
  - classes: airplane, beltloader, gse, person; one tracker per event;
  - the v1 `state_dict` keys the RT modules read:
    - the optical-flow arrival block, for 8 modules;
    - the GSE motion counters, for gse-chocks.
- **Per-frame streams** (GmStream, TrackerStream) inside `pf/rt` replace the rows read from files. A frame is held until
  the tracker has published its record.

## Acceptance

- [ ] **Row parity** with the batch GM v2 / Tracker v2 files on whole test-set videos:
  - GM within the L1 tolerance of PF-Q1-16;
  - tracker byte-identical under the seed.
- [ ] **Verdicts:** the group-A modules give batch-identical verdicts on live GM v2 + Tracker v2, not only on replayed
  production rows.
- [ ] **Frame budget** on a free machine:
  - GM + tracker + decode ≤ 35 ms per frame per camera, with the tracker ≤ 15 ms;
  - TensorRT only behind its gate (ADR-003).
- [ ] **Memory** per camera session measured.

## Plan

1. GmStream in `pf/rt`: three heads in parallel, a TensorRT flag, decisions sent to the context component.
2. TrackerStream with the exact fast paths; the publication delay handled in the runtime.
3. Whole-video runs: row parity, group-A verdicts, budget and memory.
4. Tracker cost down to ≤ 15 ms: the `estimate_sigma`, optical-flow and ReID items of PF-Q1-17.

## Experiment: pushback-pathway with GM v2 + Tracker v2 in the loop (2026-09-15, night)

Approach agreed with the lead: start with one module, build the real-time GM and tracker for it, grow them module by module
while the frame budget holds, then add the stage detector to schedule the modules.

**Setup.**
- Code:
  - `pf/rt/pipeline.py` (`RtPipelineAdapter`): each decoded frame → GM heads → causal second-run rows → Tracker v2 → the
    published records go to the unchanged production module (`pf/rt/prod_module.py`, `metadata="live"`);
  - `TrackerOptions.classes` scopes the tracked classes;
  - `scripts/rt_gm_scope_check.py` checks a dropped GM head on recorded rows;
  - `scripts/rt_pipeline_run.py` runs a configuration and compares it with the batch files.
- Video: zHxIAF2vUGxJ (cone camera, 17 280 frames, 36 min), 3.75 s GOP chunks.
- Machine: RTX 5070 Ti; the test set was drained for the runs.
- Module: pushback-pathway-confirmed-clear-of-obstacles. It is critical, single-pass and pixel-free, and it reads 10 GM
  classes and only the airplane track.

**Full GM + tracker (three heads, four tracked classes), speed 8 = no real-time pacing, `pp1_full_x8`:**

| check | result |
|---|---|
| verdict and report | **identical** to the batch run on GM v2 + Tracker v2 (Pass, same report text); decided at frame 11 847, before the session closed |
| airplane tracker records vs batch Tracker v2 (seed 0) | **9 545 / 9 545 frames identical** (box, status, arrival and departure frames); T_ARR 2 884, T_DEP 11 727 in both |
| GM rows handed to the module vs batch second-run file | without obstacle rows: 172 466 / 172 466 detections, pair recall 1.0, 93 % of frames byte-identical (the rest: the running aircraft height mode in the class-2 conf slot, which the tracker ignores after creation) |
| obstacle rows | differ: the batch file applies the final layout from frame 1, a causal branch cannot (`docs/analysis/streaming_v0.md`); pushback-pathway reads them only for drawing |
| cost per frame | total 63.2 ms mean (p50 58.7, p95 103.6, p99 174): GM 28.7 (three heads in parallel 24.3, of which postprocess 5–9 ms per head on the CPU), tracker 33.3 (DeepSORT 11.4, beltloaders 11.9, airplane 4.5, GSE 2.8, noise gate 2.7), second-run rows 0.1, module 1.1 |
| other | records published ≤ 61 frames after their frame (the airplane buffer around arrival); process memory 7.7 GB |

**Scoping GM for this module.** Dropping the vehicle head changes only the vehicle, obstacle and side_obstacle rows. The
other rows are identical on 17 280 / 17 280 frames (`scripts/rt_gm_scope_check.py`), and neither the tracker nor
pushback-pathway reads those three classes. So for this module the head is dropped with an EXACT gate.

**Scoped GM + tracker for this module** (heads gm + chocks, tracked class airplane only), speed 8, `pp2_scoped_x8`:

| check | result |
|---|---|
| cost per frame | **total 27.6 ms mean** (p50 23.3, p95 58.4, p99 139) against 63.2 for the full pipeline: GM 20.2 (two heads 15.8), tracker 6.5 (airplane 4.6, noise gate 1.6), module 0.8; process memory 5.6 GB against 7.7 |
| GM rows | the same as the full run: identical without obstacle rows (the vehicle head drop is EXACT for this module) |
| airplane records vs batch | boxes 9 545 / 9 545 identical; **status identical on 8 998 / 9 545 (94.3 %)**; T_ARR 2 884 identical, **T_DEP 11 769 against 11 727 (+42 frames, +5.3 s)**; first difference at frame 6 045 (`proceeding` in batch, `stopped` live) |
| verdict | Pass as in batch; the report text differs in the time window, shifted by the later departure: 00:24:01–00:24:46 against 00:23:56–00:24:41 |

The scoped tracker is **not EXACT**. Dropping the beltloader, GSE and person tracking changes two inputs of the airplane
logic:
- the `np.random` draws: keypoint sampling in `FeatureTracker` shares the global generator with the dropped objects;
- the frames on which the noise gate estimates sigma (`any_object` counts the dropped tracks).

Production runs the tracker unseeded, so it is exposed to the same kind of variation run to run.

Consequences:
- A tracker scoped to fewer classes goes through the NEAR gate: verdict parity on the monthly events, not byte parity.
- Follow-ups:
  - measure how much the departure frame moves between seeds with the full tracker on the same rows;
  - consider a per-object random generator and a noise gate on detections, which would make scoping exact by design.

**TensorRT fp16 heads** (the scoped configuration with `provider=tensorrt`, cached engines, speed 8, `pp4_scoped_trt_x8`):

| check | result |
|---|---|
| cost per frame | **21.7 ms mean** (p50 16.9, p95 58.1): GM 12.2 (two heads 7.4, inference ≈ 4 ms per head), tracker 8.5, module 0.8; memory 4.9 GB |

| GM rows vs batch (CUDA) | **not tolerant-equal**. Without obstacle rows, 199 035 detections against 172 466 and pair recall 0.84. The difference is not fp16 noise but a changed class distribution: chock 20 811 → 51 244 (most of the extra ones below 0.5 confidence), air_conditioning 3 → 20 814, trailer 15 818 → 27 749, tow_bar 5 → 3 503, while person, safety_vest, beltloader, cone and the aircraft parts each lose 15–20 % |
| airplane records | 4 140 of 12 860 frames identical; T_DEP 11 790 against 11 727 (+63 frames) |

So TensorRT is **not usable for real time yet**. ADR-003 measured tolerant parity (pair recall 99.9 %) on 600 frames of
another video, with RGB input (`prod` variant) and all three heads. This run differs in three ways:
- the input is BGR (`entity_clip`, the variant the monthly test set uses);
- only two heads run;
- the engines come from a cache built on 2026-09-14.

Hypotheses to check before the L2 gate of ADR-003:
1. an engine-cache mismatch — rebuild the engines in an empty cache and rerun a 5-minute slice;
2. higher fp16 sensitivity on BGR input — run `scripts/gm_bench.py` with CUDA and TensorRT on the same frames with
   `bgr_to_rgb=False`.

TensorRT at real-time speed (`pp5_scoped_trt_rt`, timing only — its rows carry the difference above): keeps up, pipeline
**20.4 ms per frame** (GM 11.7, tracker 8.1, module 0.5; p95 52), frame latency p50 2.33 s / p95 3.73 s / max 4.18 s (the
queue in front of the pipeline drops from 0.33 to 0.23 s at p50), verdict Pass 3.7 s after the deciding frame, memory 4.9 GB.

**Full pipeline at real-time speed** (control, `pp6_full_rt`): keeps up (drift −0.0002 s per recording minute).
- **Cost:** **57.1 ms per frame** (GM 26.2, tracker 30.2 — DeepSORT 10.7, beltloaders 10.6, airplane 4.0, GSE 2.6, noise gate 2.3;
  module 0.6; p95 90).
- **Frame latency:** p50 2.90 s, p95 3.80 s, max 4.71 s (the queue in front of the pipeline takes 0.76 s at p50: a chunk's 30 frames
  need ≈ 1.7 s).
- **Verdict:** report **identical** to batch, emitted 4.5 s after the deciding frame. Memory 7.7 GB.

### Summary of the configurations (zHxIAF2vUGxJ, pushback-pathway)

| configuration | ms per frame (mean / p95) | keeps up at 8 fps | frame latency p50 / max | verdict and report vs batch | airplane records vs batch |
|---|---|---|---|---|---|
| full GM (3 heads, CUDA) + full tracker | 57–63 / 90–104 | yes | 2.90 / 4.71 s | identical | 100 % |
| scoped GM (gm + chocks, CUDA) + airplane-only tracker | 27.5 / 59 | yes | 2.44 / 4.46 s | Pass, report window +5 s | 94 % state, T_DEP +42 frames |
| scoped with TensorRT heads | 20.4 / 52 | yes | 2.33 / 4.18 s | Pass, report window +16 s; detections differ | 32 % |

What the numbers say:
- **Budget.** The unmodified GM + tracker already fit the real-time budget for one camera (57 ms of 125).
- **Exact cut.** Dropping the unused vehicle head is exact and saves ≈ 8 ms.
- **Tracker scoping.** Dropping tracked classes saves ≈ 25 ms more, but it is not exact. It needs the NEAR gate, or a per-object
  random generator, before it is used.
- **TensorRT.** Not usable until its detection difference is explained.
- **Latency.** The latency floor is the 3.75 s chunk (1.94 s at p50), not the compute.
