## Scope

The scope is fixed by the real-time module list v1: 22 modules, in groups A, B and C.

- **GM:**
  - all 26 decision classes and all three heads (main, chock, vehicle), because the RT modules read every class;
  - camera, aircraft-type and entity decisions go to the context component (PF-Q2-14).
- **Tracker:**
  - classes: airplane, beltloader, gse, person; one tracker per event;
  - the v1 `state_dict` keys the RT modules read:
    - the optical-flow arrival block, for 8 modules;
    - the GSE motion counters, for gse-chocks.
- **Per-frame streams** (GmStream, TrackerStream) inside `pf/rt` replace the rows read from files. A frame is held until
  the tracker has published its record.

## Acceptance

- [ ] **Row parity** with the batch GM v2 / Tracker v2 files on whole test-set videos:
  - GM within the L1 tolerance of PF-Q1-16;
  - tracker byte-identical under the seed.
- [ ] **Verdicts:** the group-A modules give batch-identical verdicts on live GM v2 + Tracker v2, not only on replayed
  production rows.
- [ ] **Frame budget** on a free machine:
  - GM + tracker + decode ≤ 35 ms per frame per camera, with the tracker ≤ 15 ms;
  - TensorRT only behind its gate (ADR-003).
- [ ] **Memory** per camera session measured.

## Plan

1. GmStream in `pf/rt`: three heads in parallel, a TensorRT flag, decisions sent to the context component.

- A tracker scoped to fewer classes goes through the NEAR gate: verdict parity on the monthly events, not byte parity.

Hypotheses to check before the L2 gate of ADR-003:
1. ~~an engine-cache mismatch~~ — **rejected 2026-09-16, 04:27**: with the September cache moved aside and the engines

What the numbers say:
- **Budget.** The unmodified GM + tracker already fit the real-time budget for one camera (57 ms of 125).
- **Exact cut.** Dropping the unused vehicle head is exact and saves ≈ 8 ms.
- **Tracker scoping.** Dropping tracked classes saves ≈ 25 ms more, but it is not exact. It needs the NEAR gate, or a per-object
  random generator, before it is used.
- **TensorRT.** Not usable until its detection difference is explained.
- **Latency.** The latency floor is the 3.75 s chunk (1.94 s at p50), not the compute.

**End-of-session marker** (done 2026-09-16, 05:20). In real time the length of the recording is not known while the camera
is still recording, but modules ask for it (`dataset.nframes`, `cap.get(CAP_PROP_FRAME_COUNT)`,
`video_worker.number_of_frames`).
- `ProductionModuleAdapter(session_length="marker")` — the default now — answers with a value no frame number reaches
  until the last frame of the session is handed over; then it answers with the real length, so a module that tests
  `frame_number == nframes` still sees its last frame. `session_length="manifest"` keeps the old behaviour for comparisons.
- The audit counts the reads before and after the marker separately.
- Checked on the live rows of the full pipeline (`marker_check_zHx`, four modules): **verdicts and reports identical to
  batch** for pushback-pathway, pushback-does-not-start, 3-stop and conditioned-air. The two modules that read the length
  did so 12 104 and 12 009 times, all before the marker, and their decisions did not change.
- Tests: `tests/test_rt_session_marker.py`.

**Shared frame ring** (done 2026-09-16, 05:24). Hosted modules that read pixels get the frames through one shared-memory
ring: the pipeline writes each published frame into a slot, the host copies it before the module sees it and acknowledges
the copy, and the pipeline never overwrites a slot that has not been copied (the first version without acknowledgements
handed modules the wrong frames as soon as the ring wrapped — caught by `tests/test_rt_module_host.py`).

**Scope tool** (`scripts/rt_scope_for.py`): for a set of modules it prints the GM heads and tracked classes they need and
the command to run them. For the three critical modules above: all three heads, tracked classes airplane, beltloader and
person — GSE is not needed by any of them.

### Per-frame transport instead of chunks (2026-09-16, `pdns_frames`)

The branch now has a second ingest (`pf/rt/runtime.py`, `--ingest frames`): every frame leaves the camera as soon as it is
encoded, as RTSP / SRT would deliver it. The uplink is modelled serially from the real frame sizes of the video
(`pf.rt.chunker.packet_sizes`): zHxIAF2vUGxJ averages 62 KB per frame, keyframes 118 KB, i.e. the documented ≈4 Mbit/s.

Transport latency alone, by uplink (whole video, arithmetic from the frame sizes):

| uplink | frame transfer p50 / max |
|---|---|
| 1 Gbit/s | 0.010 / 0.011 s |
| 10 Mbit/s | 0.059 / 0.121 s |
| 6 Mbit/s | 0.092 / 0.195 s |
| 4 Mbit/s | 0.416 / 0.739 s — the link carries exactly the bitrate, so frames queue |

Whole event with GM + tracker + pushback-does-not-start at real-time speed, 10 Mbit/s, quiet machine:

| | 3.75 s chunks (1 Gbit/s) | per frame (10 Mbit/s) |
|---|---|---|
| frame latency p50 / p95 / max | 2.69 / 3.79 / 4.52 s | **0.110 / 0.163 / 0.937 s** |
| verdict after the deciding frame | 3.0 s | **1.05 s** |
| frame queue, max | 29 | 4 |
| pipeline cost | 42.7 ms | 44.1 ms |
| verdict | Fail, identical to batch | Fail, identical to batch |

Latency components at p50: link 0.059 s, receiver and queue 0.008 s, decode 0.003 s, pipeline 0.040 s; the chunk wait is
gone.

Two consequences:
- **The uplink must have headroom over the bitrate.** At 4 Mbit/s for a 4 Mbit/s stream the queue alone costs 0.4–0.7 s;
  at 10 Mbit/s it is 0.06 s.
- **The next latency term is the tracker, not the transport.** A frame is processed in 0.11 s but the verdict takes 1.05 s,
  because the tracker publishes a frame's records only after its N_INIT delay of 8 frames (1 s) — production behaviour,
  kept for parity. Shortening it is a tracker decision (PF-Q1-17), and it is now the biggest single term left.

### Rehearsing on the minutes that decide (2026-09-16)

`scripts/rt_slices.py` cuts an event down to the stretches where the modules actually decide. The windows are not a
guess: every batch module output carries `smart_timeline` with the frames it decided on. The tool reads them for the
real-time module set, adds a pre-roll (the tracker and the GM context need history), merges what overlaps, snaps the
start to a keyframe and cuts with stream copy — every frame bit-identical to the source.

zHxIAF2vUGxJ (36.0 min, 17 280 frames), the three real-time modules:

| module | batch verdict | decided on frames |
|---|---|---|
| pushback-pathway | Pass | 11 487–11 847 (23.9–24.7 min) |
| pushback-does-not-start | Fail | 11 595–11 836 (24.2–24.7 min) |
| 3-stop-brake-check | Fail | 8 905 (18.6 min) |

With a 4-minute pre-roll the windows merge into **one contiguous slice, frames 6 961–12 007 — 10.5 min, 29 % of the
event**, covering all three modules (`out/rt/slices/zHxIAF2vUGxJ_6961_12007.mp4`, its chunk folder next to it).

What a slice is: a **pseudo-event**. Frames are renumbered from 1, the modules see a session of that length, and the
report timestamps are relative to the slice. A module whose decision needs more history than the pre-roll can therefore
answer differently than on the whole event — so `--run` compares each slice verdict with the whole-video batch verdict
and prints which modules survive the cut. Use the survivors for real-time rehearsals; parity still belongs on whole
events.

**First rehearsal on the slice** (`slice_clean`, frames 6 961–12 007, per-frame ingest at 10 Mbit/s, real-time speed,
test set suspended, all three modules on one live GM v2 + Tracker v2):

| | |
|---|---|
| keeps up | yes — drift −0.001 s per recording minute, 782 s of wall clock for 10.5 min of recording |
| pipeline | **64.6 ms per frame** of 125 (GM 23.7, tracker 37.4, modules 3.3 in the loop), memory 7.5 GB, max frame queue 6 |
| frame latency | p50 **0.13 s**, p95 0.24 s, max 1.0 s |
| verdict latency | 0.85–1.09 s after the deciding frame (the tracker's 1 s publication delay is most of it) |

| module | on the slice | on the whole event (batch) | |
|---|---|---|---|
| pushback-pathway | Pass, "no transport on the pushback pathway on the departure stage (00:09:30–00:10:15)" | Pass, frames 11 487–11 847 | **same** — the same window, shifted by the slice offset |
| pushback-does-not-start | Fail, "left side obstructed, no wing-walkers on the right (00:09:47–00:10:17)" | Fail, frames 11 595–11 836 | **same** |
| 3-stop-brake-check | Not observed, "No stopped beltloaders were detected" | Fail at frame 8 905 | **different** — the beltloader's stops happen before the slice starts |

So the pushback pair rehearses honestly on a few minutes, and 3-stop does not: it counts what the beltloader did since it
approached, which is roughly ten minutes before its verdict. The planner therefore takes the pre-roll from the data —
the first frame where the tracked classes the module reads appear (`docs/analysis/module_consumption.json` +  the batch
tracker file) — bounded by `--max-pre-minutes` (default 8), because the class alone is a weak proxy: a beltloader is
somewhere at the gate from frame 10. With that, the same three modules plan into one 14.5 min slice; the verdict check
of the longer pre-roll for 3-stop is the next run.

Second thing the rehearsal showed: **the decisive minutes are the expensive minutes.** The branch costs 64.6 ms per
frame there against 44 ms on the quiet first seven minutes of the same event — more objects, more tracking. Timing a
real-time budget on the quiet part of a recording underestimates it by about a third.
