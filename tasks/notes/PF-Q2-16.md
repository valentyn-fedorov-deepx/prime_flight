## Two production stacks on one branch

The bucket file name is the commit the image was built from (`general_model<git rev-parse --short HEAD>.ndjson`,
`db_worker/ML_worker.py`, `upload_infereces_to_cloud_storage`). So the a0157a4 file of 2026-10-13 came from an image built
at a0157a4, and the branch head d4ae8e5 is a different stack with the same GM code:

| | a0157a4 (2025-09-04) | d4ae8e5 (2025-12-09, branch head) |
|---|---|---|
| base image | `gpu_base:legacy_base`, python 3.8, cuDNN 8.2.4 | `gpu_base:python_3_10_cudnn8`, torch 1.13.1+cu117, onnxruntime-gpu 1.15.0 |
| cv_common | d74eb09 | ac5098d ("fix plane arrival timing") |
| db_worker | 2fd7325 | 5a4aa83 (README only) |
| GM code | | unchanged (`run_module.sh` added) |

Our branch (afaebf1) sits on d4ae8e5. The 99.95 % agreement of a0157a4 and afaebf1 on Bdx1iGrXPEfe compares the two
stacks, not the MR; on one stack the MR is byte-identical (`tasks/notes/PF-Q4-02.md`).

## Steps

1. **Confirm the production image** (Maksym): built at a0157a4 or at d4ae8e5 — the commit in the GM file names of fresh
   production videos says which. It decides where the MR goes: on d4ae8e5 as pushed, or onto a0157a4 (the two commits
   apply cleanly there too, but that stack pins cv_common d74eb09, which we cannot read, so it needs its own identity run).
2. **Build the baseline** = d4ae8e5 plus Maksym's two image commits, without the MR:
   `git checkout -b pf/q4-02-baseline d4ae8e5 && git cherry-pick bc61b5e afaebf1`. Checked 2026-10-21: it applies
   cleanly, and its difference from afaebf1 is exactly the MR's four files (+80 / −41). d4ae8e5 alone is unlikely to run
   today: dvc 3.4.0 breaks on pathspec ≥ 0.12, and the font download in cv_common fails on python 3.10.
3. **Run it on 3–5 of the 90 videos** (Bdx1iGrXPEfe among them), on the node type of the afaebf1 run; note the job time
   of both. Compare `general_model<baseline>.ndjson` with `general_modelafaebf1.ndjson` **after gunzip**: the objects are
   gzip files with the file time in the header, so the bucket md5 / crc32c differ even for the same content.
   Expected: byte-identical.
4. **If identical**, the afaebf1 files of the 90 videos are the production code's output on this stack: no re-run of the
   90. Oksana scores them per task next to the April-2024 scores (the CSV of 2026-10-17, `gm-files-for-score-drop.csv`,
   shows drops on 56 of 90 videos, worst on safety huddle, pre-departure walk-around, pin verification, handrails on GSE,
   cones removed, steering, hand signals, safety zone). **If not**, `pip freeze` of both images, the baseline on all 90,
   and the tolerant comparison per video (`pf.eval.parity.compare_gm_ndjson_tolerant`).
5. **Point the monthly test's GM baseline at the production branch head**, so it moves when production does.

## Pitfalls

- Trackers and modules load the newest GM file of a video unless `general_model_inferences_version_commit` is set
  (`db_worker/model_starter.py`): pin it for scoring. Tracker files are named by the tracker's commit, so tracker runs on
  two GM files of one video overwrite each other.
- `frame_stopped` and `confidence_camera` in the report differ between two runs of production itself (unseeded
  `np.random` in cv_common): compare the ndjson.
- If production runs the a0157a4 image, deploying the branch head, with or without the MR, also switches the stack: the
  detections move at the 99.95 % level. Its effect on verdicts alone needs the a0157a4 image on the 90 videos (optional).

## Acceptance

- Baseline and afaebf1 byte-identical on 3–5 videos (or every difference explained by the image); job times of both.
- Module scores of the production code on the 90 videos, per task, next to the April-2024 ones.
- The monthly test configured with the production branch as its GM baseline.
