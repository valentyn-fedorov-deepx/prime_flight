## Steps

1. **Production baseline**: the deployed production image on the 90 videos → `general_modela0157a4.ndjson` for each.
   The 13.10 file of Bdx1iGrXPEfe is kept locally (`out/testset/gm_prod/`), so the rerun also shows whether the cluster
   reproduces itself. First a few videos (2026-10-21); suggested: Bdx1iGrXPEfe; b8ijKDWsLlQi8W, the largest drop in the
   CSV (−49 over 7 tasks); fAkpu3dj2NIj, whose baseline is 342fd00, already RGB, so a drop that stays there is not BGR vs
   RGB; n96M7fASlhGn and 7PytHarRNqmT (−31.5 / −30.9, on disk locally).
2. **The MR on production's stack**: branch `pf/q4-02-gm-exact-speedups-a0157a4` @ 8d8c9a4 = a0157a4 + the two commits
   (cherry-picked cleanly, the same diff as the pushed branch, python 3.8 grammar checked; local, push on request). Build
   it as the production image with only the four files and `.git` swapped — without the new `.git` its output is named
   a0157a4 and overwrites step 1's files. Run it on 3–5 of the 90 videos (Bdx1iGrXPEfe among them), note the job time of
   both, compare with step 1 **after gunzip** (the objects are gzip files with the file time in the header, so the bucket
   md5 / crc32c differ even for the same content). Expected: byte-identical. Our proof ran with cv_common ac5098d;
   production pins d74eb09, which we cannot read, so this run is the proof on production. The MR newly imports
   `check_bounding_box` (`cv_common.common`) and `Status` (`cv_common.tracked_object`); both are in every cv_common
   version on disk.
3. **Scores**: Oksana scores step 1's files per task next to the April-2024 scores (the CSV of 2026-10-17,
   `gm-files-for-score-drop.csv`, shows drops on 56 of 90 videos, worst on safety huddle, pre-departure walk-around, pin
   verification, handrails on GSE, cones removed, steering, hand signals, safety zone).
4. **Monthly test baseline** = the deployed production image from now on, so it moves when production does.
5. **If step 2 is identical**: the MR goes onto a0157a4 as a drop-in (same outputs, about 0.8 of the GM time). If not:
   both files of one video to us.

The afaebf1 files stay useful for one question: with step 1 they measure the d4ae8e5 stack (python 3.10, new base image,
cv_common ac5098d) on the 90 videos, should production ever move to it.

## Pitfalls

- Trackers and modules load the newest GM file of a video unless `general_model_inferences_version_commit` is set
  (`db_worker/model_starter.py`): pin it for scoring, as `a0157a4.ndjson` — the loader does not add the extension
  (`ML_worker.py`, `load_inferences_from_cloud_storage`). Tracker files are named by the tracker's commit, so tracker runs on
  two GM files of one video overwrite each other.
- `frame_stopped` and `confidence_camera` in the report differ between two runs of production itself (unseeded
  `np.random` in cv_common): compare the ndjson.

## Acceptance

- `general_modela0157a4.ndjson` from the deployed image for all 90 videos.
- The MR on a0157a4 byte-identical to it on 3–5 videos (or every difference explained), job times of both.
- Module scores of production on the 90 videos, per task, next to the April-2024 ones.
- The monthly test configured with the deployed production image as its GM baseline.
