# PF-Q2-13 · Real-time components: what a module declares, when it is open, where its outputs go

- **Owner:** Valentyn (+agents) · **Agents:** pipeline-architect + gm-tracker-engineer · **Status:** in-progress · **Quarter:** Q2
- **Deps:** PF-Q1-19, ADR-004 · **Related:** PF-Q1-03 (stage events), PF-Q2-02 (the branch), PF-Q3-01 (alert service)

## Why

The branch ran the modules as one block: every hosted module got the same whole record, all of them ran for the whole
session, and an output waited for the next frame of the pipeline before it left the process. Nothing in that is a module
property — it is the absence of a contract between the pipeline and a module. ADR-004 wrote the contract; this is the
implementation of the three parts that make a module a component.

## What a component is now (`pf/rt/component.py`, `pf/rt/module_host.py`)

| part | what it means | where it comes from |
|---|---|---|
| **declared inputs** | the GM classes, the tracked classes and the tracker state a module reads; anything else is dropped before the record is handed over | `docs/analysis/module_consumption.json` (static analysis of the module code), not hand-written |
| **gate** | `open_on` / `close_on` stage events with a look-back; a component opens late and closes when its stage is over | `pf/rt/gating.json` (proposal, unreviewed) |
| **outputs** | an `OutputBus` with sinks; a reader thread publishes the moment the module produces an output | the component shell, not the frame loop |

Mechanics worth knowing:

- **Two one-way pipes per component.** Frames go parent → child; outputs and ring acknowledgements come child → parent, so
  the reader thread and the frame loop never touch the same handle.
- **The module keeps its own frame numbering.** A production module enumerates its session from 1. A gated component opens
  at, say, frame 11 487, so `LiveFeed` shifts absolute ids into module numbering and shifts every output back: what leaves
  the branch is always an absolute `frame_id` (X2).
- **Sinks.** `component_outputs.ndjson` is written per run as outputs appear; `http_sink(url)` POSTs each output from a
  background thread (best effort, never on the frame path) — that is the seam for the alert service (PF-Q3-01).

## What a declared subscription saves (measured, 400 frames from the middle of zHxIAF2vUGxJ)

The frame record the branch hands a module averages **13.5 KB** (29.7 GM rows and 5.2 track records per frame).

| component | record it is given | of the whole | cost to filter |
|---|---|---|---|
| 3-stop-brake-check | 1.91 KB | 14 % | 0.011 ms |
| pushback-pathway | 1.62 KB | 12 % | 0.005 ms |
| pushback-does-not-start | 1.64 KB | 12 % | 0.004 ms |
| beltloader-chocks | 2.56 KB | 19 % | 0.007 ms |

The class filter alone is not what does it: dropping the classes a module never reads leaves 58–90 % of the record. **76 %
of the record is the tracker's own optical-flow state** (`_p0`, `_st` — the point clouds it uses for tracking), and no
real-time module reads it: they read `_status`, `_obj_id`, `_color`, `_xyxy`. Dropping it is the same decision as the v2
bus in PF-Q1-17, made per component from its declaration.

So the honest summary: at 8 fps and three components the saving is ~0.3 MB/s, which the machine does not feel. It matters
for what it makes possible — a component that receives 1.6 KB per frame can live in another process, another container or
another machine, and can be reasoned about on its own.

## Gating: what the first run taught

The first run with the table switched on starved every module: the gates named `BL_LEAVE`, `PUSHBACK_ATTACHED`, `T_ARR`,
and **nothing publishes those events yet** (the stage detector is PF-Q1-03), so no component ever opened and none of them
saw a single frame. Fixed by making gating explicit: `Gate(spec, enabled=False)` by default — the table is reported in
every run, applied only when an event source is wired. The regression is a test.

That is the whole risk of gating in one sentence: a gate is a promise that someone else fires the event.

## Status of the safeguards

- **Subscriptions are opt-in** (`--subscriptions`): a wrong declaration silently starves a module, so they are gated by
  verdict parity, exactly like the scoped GM heads and tracker classes (PF-Q2-02).
- **Gating is opt-in** and needs PF-Q1-03 before it can be measured at all.
- **Outputs on the bus** are on by default: they change when an output leaves, never what it says.
