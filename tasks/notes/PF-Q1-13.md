## Key points
1. The tracker is a per-video, **pixel-reading** batch job: OpenCV decode + the GM second-pass ndjson zipped positionally.
   No chunks, no `frame_id`, no `schema_version`, no resets, no events exist in the code.
2. Engines: **three DeepSORT instances** (BL/GSE: MAX_AGE 160, N_INIT 8; person: 100/6) plus one `Airplane(obj_id=1)` fed by
   the GM class-2 row. "MAX_AGE 40 / MIN_HITS 8" quoted on the stand are GM's norfair parameters, not the tracker's.
3. Envelope = `Track` dataclass `__dict__`: `tr_id, xyxy, cls_str, conf (always 0.0), state_dict, data`; `_obj_id` is the
   object's first track id and survives re-association, `tr_id` is the DeepSORT id → they differ and collide across classes.
4. `state_dict` = exactly 32 base keys + 7 airplane (39) / + 2 vehicle (34) / person `{}`; `from_state_dict` on the current
   family raises `ValueError` on any unknown key (tolerates only `_recent_bboxes*` and `arrival_frame`).
5. Status machine: optical flow on ≤ 250 keypoints inside a segmentation mask; transitions at 24 / 8 / 16 / 5 frames exactly
   as observed in the data; `_is_stopped` nulls come from the per-update reset; `is_stopped` = `status == STOPPED`.
6. `arrival_frame` = start S of the stopping episode, but it is only known at S+57 frames and written **retroactively**
   via a 5-frame buffer + a rewrite of the airplane data buffer (source of the extra envelope key); `departure_frame` =
   80 moving frames after motion start (causal); `have_pre_arrival_stage` = "arrival after ≥ 60 s of footage".
7. BL semantics: `data.bl_type` is door-based (overlap + 60 % rule for ≥ 8 stopped frames), keyed by `tr_id`, cleared on MOVING;
   no BL↔aircraft IoU, no pushback track, no event edges — T_arr / T_dep / BL@door / BL leave are derivable today,
   `pushback_attached` is not.
8. Non-causal / ordering hazards: the arrival rewrite, person tentative back-fill, an EOF flush that can mis-assign frame keys,
   **unseeded `np.random`** in keypoint sampling — two v1 runs are not guaranteed bit-identical.
9. Version drift: only ac5098d of the 11 module pins is in the archive; the pre-2025 `__dict__` family accepts any key
   (38/40-key variants), the 2025+ explicit family (39/34) raises — adding a `state_dict` key breaks every module on the new family.
10. **Production bd43c3c** keeps the same key set and event semantics but swaps MobileSAM for two YOLO-seg models (with a
    BL/GSE cache-key collision), throttles the noise gate to 1/16 frames and repairs bad boxes; it cannot run on the
    cv_common it pins (ac5098d) — its `update_params(..., frame_number, segmentor, yolo_idx=...)` matches the
    `tracker_optimization` line (2759daf) → the exact cv_common in the production image is unknown (§11.9).
11. `02_target_architecture.md` §6 "tracker 0.11 ms" is a hard-coded replay constant of the stand (`simulate.py:305`);
    the real `cv_trackers` cost has never been measured.

## Consequences for Tracker v2 (PF-Q1-17) and the stage detector (PF-Q1-03)
- v1-compat: keep the envelope, the exact key set per class, Status strings, `_obj_id` semantics; write `_p0/_st` only in
  the v1-compat file. New fields/events → `data{}` / `anchors` only (ADR-001 §3).
- Determinism: seed the keypoint sampling (or make it deterministic) — otherwise parity between two runs is impossible.
- Events: T_arr / T_dep / BL@door / BL leave can be emitted from existing state; `pushback_attached` needs new geometry.
- Parity backend: ATL-C5 files were produced by bd43c3c with YOLO-seg masks, so the parity target for Tracker v2 is that
  backend; the seg weights are in the production `weights.dvc` of the tracker (not pulled yet).
