## Why

The stage detector decides which modules run on which frames. In real time it is both the cost lever and the correctness
lever:
- **cost:** only the modules of the current stage run — 4–9 instead of 27;
- **correctness:** one owner of T_ARR, BL at door and pushback attached, instead of 9 local copies in the modules.

The real-time module list v1 (`docs/analysis/rt_module_selection.md`) fixes which events are needed.

## Scope

1. **Causal state machine** over the tracker records and GM rows:
   - stages PRE_ARRIVAL → ARRIVAL → POST_ARRIVAL → DOWNLOAD / UPLOAD → PRE_DEPARTURE → DEPARTURE → END;
   - `undetermined` when the view does not allow a decision.
2. **Events and anchors on every frame** (ADR-004):
   - T_ARR, BL_AT_DOOR (per belt loader), BL_LEAVE (last belt loader), PUSHBACK_ATTACHED, pushback moving, T_DEP,
     T_DEP + 60 s, the end-of-session marker;
   - derived deadlines: T_ARR + 30 s (nose gear) and T_ARR + 240 s (steering pin).
3. **Gating table** for the 22 real-time modules:
   - cameras by aircraft type, from the client split via PF-Q2-14;
   - open and close events, look-back frames;
   - conditioned-air opens at T_ARR, because it keeps whole-event hose history; pushback-pathway opens at BL_LEAVE.
4. **Evidence per decision:** frame ids and the signal that fired, so a question like "why was this stage missed" gets a
   number as the answer.

## Starting points

**Code in this repo:**
- `pf/tracker/events.py` — T_ARR, T_DEP, BL_AT_DOOR and BL_LEAVE, derived causally from the published tracker records.
  On DjwtQRdZyt0sSk they are identical to production: T_ARR 3 669, front door 9 888–22 776.
- `pf/stage/pushback.py` — PUSHBACK_ATTACHED with aircraft-chocks' causal nose rule.
  - It gives the production frame on 5 of 7 ATL-C5 videos.
  - On the other 2 (−183 / −18 frames), production uses a look-ahead median rule that has no causal equivalent.

**Stage-boundary study in `G:\gat_stages`** (August 2026, 88 labelled events):
- documents:
  - `STAGE_BOUNDARIES.md`: 8 boundaries with signal, rule and readiness;
  - `REPORT.md`: what production does today;
  - `IMPLEMENTATION.md`: rollout phases and measured blockers.
- labels: `gt_dataset.tsv`, `gt_confident.json`, `gt2_dataset.csv`.
- rollout phases:
  1. windows only: 73–76 % of module frames saved, with no coverage risk;
  2. gating by camera and aircraft type;
  3. skipping by stage, per category, only after its false-`absent` rate is measured near zero.
- measured blockers:
  - **departure:** `PlaneDepartureDetector` needs an 18 % bbox shrink, but a real departure shows 3.2 %, which gives 9 false
    `absent`. The drop of part heights below the presence threshold (tail 272 → 147 → gone) already works for arrival in
    `presence.py`.
  - **broken camera view:** a camera looking into a vehicle cabin for 18 minutes must give `undetermined`, not `absent`.
  - **several events in one video:** they get stitched together.
  - **wing camera:** the belt loader logic is not implemented, so Download / Upload is always `undetermined`.
  - **jets:** coverage never checked.
  - **Upload:** in 62 of 94 videos the belt loader does not leave, so it cannot separate Download from Upload.

**Inputs without live GM / tracker:**
- production tracker and GM ndjson of the 90 test-set videos (`out/testset/prod/`, bucket `cv-modules-topics`);
- the GM v2 / Tracker v2 outputs of the same videos;
- replay in real time with `pf/rt/simulate.py`.

## Acceptance

- [ ] Causal: every event fires within its declared latency and never from future frames. Replay test: the events stay
  identical when the stream is cut at any frame.
- [ ] T_ARR and T_DEP equal the production tracker's `arrival_frame` / `departure_frame` ±1 frame on the 90 test-set
  videos, or every difference is explained.
- [ ] Stage boundaries on the 88 labelled events are at least as good as in the August study, per boundary; false `absent`
  counted per category.
- [ ] PUSHBACK_ATTACHED is checked against the production frames of aircraft-chocks and pin-verification on the module
  sample; differences explained.
- [ ] Gating parity: the group-A modules give the same verdicts gated as always-on on the module sample (10 events).
- [ ] Latency report in the RT runtime: each event's latency from the capture of the frame that makes it true.
