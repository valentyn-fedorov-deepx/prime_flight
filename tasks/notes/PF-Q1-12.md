## Головне (для того, хто не читатиме 375 рядків)
1. GM-job = одне full-turn відео однієї камери; `model_starter.py` з db_worker: `dvc pull` → `detect()` → gzip-ndjson у
   `gs://cv-modules-topics/<video>.mp4/general_model<commit>.ndjson` + Kafka-звіт. MongoDB GM не чіпає.
2. `detect()` робить **три повні проходи** по відео (3 readers відкриті наперед + четвертий у `get_video_info`):
   1) 3 ONNX YOLOv8 (GM@1088, chocks@1280, vehicle@1088) + Norfair/SAM трекінг літаків; 2) повторний декод + збагачення;
   3) `select_video` frame-diff, результат якого ніхто не читає.
3. Модулі й трекер читають **файл другого проходу**: сирі рядки `airplane` викинуто, один головний літак на кадр із
   **модою висоти (напр. 680) у conf-слоті**, рядки `obstacle`/`side_obstacle` = копії боксів зі сталим `conf`
   (`main.py:823, 829`). Формат рядка `[x1,y1,x2,y2,conf,cls]`, 1-based ключі = лічильник writer-а, без `schema_version`.
4. Per-video рішення: головний літак, висота-мода, layout частин, стадії — **потрібне все відео** (argmax після EOF);
   тип камери — інкрементна більшість, але фіналізується після EOF (є невикористане 20-хв вікно `main.py:734`);
   entity (40 хітів) і тип літака (500 голосів) — вирішуються рано.
5. Мертве/зламане: BL-стадії завжди False (`front_door`/`back_door` ніколи не наповнюються), `stages=None` у звіті,
   noise/`is_broken` губляться на межі job, CPU-режим непрацездатний (`.cuda()` без умови), `timm(pretrained=True)` тягне ваги з мережі.
6. Перф: batch=1 скрізь, ≈41 % обчислень на паддінгу квадратних входів, per-row GPU→CPU синхронізації, SAM щокадру,
   `write_video` default True у проді.
