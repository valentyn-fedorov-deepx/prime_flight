# PF-Q1-19 — Real-time branch prototype: chunked ingestion simulated end to end

**Owner:** Valentyn (+Maksym Ch.) · **Agents:** pipeline-architect, module-porter · **Status:** in progress (started 2026-09-15)
**Related:** PF-Q1-02 (receiver), PF-Q2-01 (RT branch), PF-Q2-03/04 (first RT modules), `docs/02_target_architecture.md`

## Goal

A basic real-time architecture: the CameraBox records short chunks, they reach the server over an (ideal) uplink, the server
processes frames as they arrive and emits outputs as soon as they exist. Simulated on the wall clock with a real test-set
video, measured per frame, with production modules running unchanged.

## Architecture (`pf/rt`)

```
CameraBox sim ──chunk closed──► uplink model ──► receiver ──release──► decoder ──frames──► module adapter ──outputs──► sink
 (3.75 s GOP chunks)   (bandwidth, RTT,        (order, loss        (OpenCV,        (production detect()   (ndjson, written
                        jitter, loss)           inference, gaps)    count check)    on live frames)        on emission)
```

- A chunk is a transport unit only: modules see frames with absolute 1-based frame ids and capture times (X2).
- `chunker` — GOP-aligned stream-copy cutting with a manifest (first frame id, frame count from packet counts, recording
  times, bytes). The DXGAT cameras write a keyframe every 3.75 s (30 frames at 8 fps), so 1 GOP = one 3.75 s chunk ≈ 1.9 MB.
- `cambox` — chunk k is ready when it closes (t_end) and arrives after RTT + jitter + bytes·8/bandwidth; `speed` compresses
  time for tests.
- `receiver` — releases chunks in recording order, waits `reorder_timeout_s` for a late chunk, then declares it lost and fills
  its frames with placeholders sized from the next chunk's first frame id (or the end-of-recording frame count).
- `runtime` — decoder thread + bounded frame queue + module loop; per-frame stamps (capture, chunk closed, arrived, decode,
  module); per-output emission time; report with latency percentiles, their components, latency drift per recording
  minute, backlog samples.
- `prod_module` — `ProductionModuleAdapter` runs a module's `detect()` unchanged in a thread with a live VideoWorker: a
  LoadImages look-alike and a metadata generator that block until the frame arrives. Audited: reads of the session length
  (unknown in real time), frames requested outside the look-back window; the module never gets the video file. Hooks
  (`pf/rt/hooks`) observe module state without changing it and emit outputs while the session runs.
- `scripts/rt_modules.py` — several modules in parallel (one process each) with the launch facts of the test set
  (`scripts/testset/profiles.py`); compares each live verdict and report with the batch result of the same video.
- Tests: `tests/test_rt_cambox.py`, `tests/test_rt_runtime.py`, `tests/test_rt_prod_module.py` (15).

## What the prototype shows so far

- With 3.75 s chunks the latency floor is the chunk itself: a frame waits on average half a chunk before its chunk can leave
  the box; an ideal gigabit link adds tens of milliseconds, decoding tens of milliseconds more.
- A module that is slower than real time is visible immediately in the report (drift, queue depth), without dropped frames.
- Production modules run unchanged on live frames and give the batch verdict. Whether a verdict can be early is a property
  of the module's logic: modules that stop at the aircraft departure answer about 2 s after the departure frame is captured
  (today: after the event, the merge and the batch jobs); safety-vests decides at the end of the session (Pass needs the
  whole session; a master Fail can revert) and its per-worker status changes are emitted live as provisional alerts
  through a hook.
- Real time needs one signal the production modules take from the file: the session length. The branch knows it only when
  the CameraBox closes the recording, so the last chunk has to carry an end-of-session marker; in the prototype the length
  is served from the manifest and every read is audited.

## Limitations (deliberate for the basic version)

- GM and tracker rows come from the production files of the same video, handed over in step with the frames (as if GM +
  Tracker had zero latency). No module of the 27 decides from pixels alone.
- One production module per process; a single camera; no stage gating.
- Measured on a machine busy with the test-set run.

## How to run

```bash
python -m pf.rt.chunker --video out/testset/videos/zHxIAF2vUGxJ.mp4 --out out/rt/chunks/zHxIAF2vUGxJ
python -m pf.rt.simulate --chunks out/rt/chunks/zHxIAF2vUGxJ --adapter probe --max-seconds 300 --out out/rt/runs/probe
python -m pf.rt.simulate --chunks out/rt/chunks/zHxIAF2vUGxJ --adapter prod --out out/rt/runs/vests --adapter-args '{"module": "safety-vests-secured-to-body", "module_dir": "external/_branches/safety-vests-secured-to-body@tdv_cone", "inferences_dir": "out/testset/prod/zHxIAF2vUGxJ.mp4", "hook": "pf.rt.hooks.vests:install", "env": {"TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD": "1", "YOLO_AUTOINSTALL": "False"}}'
python scripts/rt_modules.py --video zHxIAF2vUGxJ.mp4 --tag rt_light_zHx --modules conditioned-air-removed-10-mins-prior-to-departure-and-properly-stowed,beltloader-chocks,pushback-pathway-confirmed-clear-of-obstacles
```
