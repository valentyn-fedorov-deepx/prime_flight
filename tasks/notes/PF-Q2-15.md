# PF-Q2-15 · What each module costs in real time, and whether it runs there as it is

- **Owner:** Valentyn (+agents) · **Agents:** qa-parity + module-porter · **Status:** review · **Quarter:** Q2
- **Deps:** PF-Q2-02 (the branch), PF-Q2-13 (a module is a component) · **Related:** PF-Q2-11 (lightening), PF-Q3-04, PF-Q4-02
- **Report:** `docs/analysis/rt_module_cost.md` + `.json` (generated by `scripts/rt_module_report.py`)

## Question

For every module: what load does it put on the machine in real time, can it run there without rework, and does it keep the
post-processing verdict. Then: what a set of modules costs together, where GM and the tracker are paid once.

## Method

| step | what ran | script | output |
|---|---|---|---|
| 1 | every module **alone** behind its pseudo-GM (only the heads it reads) and a tracker with only its classes, on its decisive minutes of `zHxIAF2vUGxJ` (≤ 6 min) at real-time speed; GPU, GPU memory, CPU cores and RAM sampled over the process tree | `scripts/rt_module_cost.py` | `out/rt/cost/zHxIAF2vUGxJ/modules.json` |
| 2 | the same, the **whole event** live (causal rows, live tracker, session length unknown), GPU kept busy; verdict and report against the batch run | `scripts/rt_module_cost.py --parity` | same file, `whole_event` |
| 3 | GM by head set and tracker by class set on one common stretch at real-time speed | `scripts/rt_shared_cost.py` | `shared.json` |
| 4 | every module over the **test set** (69 events) with only its scoped rows against the full rows (`mod:sub` against `mod:v2`) | `scripts/testset/orchestrate.py`, `scripts/run_module.py --subscription` | `out/testset/modules/sub`, `out/testset/compare_sub_vs_v2.json` |
| 5 | the modules that run as they are, **together** on the whole event: one GM, one tracker, every module its own process | `scripts/rt_joint_run.py` | `joint_*.json` |

The scope of a module comes from its declaration (`pf/rt/component.py`: static analysis + `pf/rt/declarations.json`).

## Result

- **20 of 27 modules run in real time as they are** with the batch verdict on the whole event: 15 with the same report during
  the turn, 3 only when the session closes (safety-vests, gse-chocks, handrails-on-gse: they need a hook for an interim verdict
  to be useful live), 2 with a small shift in the report caused by the scoped tracker (cones-placed, pushback-pathway).
- **4 cannot**: aircraft-chocks, hand-signals, pin-verification, safety-zone read the session a second time from frame 1
  (`KeyError: 1` live). Already planned: PF-Q3-04 and PF-Q2-11.
- **3 are not hosted** by the branch: both walk-arounds (own Python environment), hair-policy (WSL).
- **Load alone**: 19–47 ms of the 125 ms budget. Almost all of it is the shared part: GM 8.5–19.2 ms by head set, tracker
  4.9–26.2 ms by tracked classes (the belt loader is the expensive class: +13–16 ms). The module itself is under 3.3 ms for
  17 of the 20; the heavy ones are safety-vests 18.8 ms and 5.5 CPU cores, handrails-on-gse 12.5 ms and 3.7 cores,
  wing-walkers 5.1 ms (p95 85 ms, frame latency p95 1.4 s in its busy minutes).
- **Together**: GM and tracker are paid once, so the 20 modules are predicted at 105 ms of 125 if every module sat on the
  frame path (sum of the single runs: 605 ms). **Measured** (all 20 in one session on the whole event at real-time speed, a
  process per module): keeps up, frame path 56.4 ms mean / 94.7 ms p95 (GM 22.4 + tracker 26.6 + hand-off 7.3), frame latency
  p95 0.21 s, GPU 24.5 % busy, +8.0 GB GPU memory, 4.2 CPU cores on average with stretches at 100 % of the 8 cores, 18.2 GB
  RAM; **20 of 20 verdicts and 20 of 20 reports identical to batch** (the two report shifts of the scoped tracker are gone
  with the full tracker). Fed as fast as it goes, the same set does 1.85x real time (67.7 ms per frame).
- **Live against batch on every event still on disk** (6 events, the modules the plan runs on each camera, together):
  **78 of 78 verdicts identical, 77 of 78 reports identical**. The one report: lead-marshaller on `MwCSLbQ7QvXQ`, Fail in
  both, the stage boundary inside the report differs (see below).
- **The one difference found live is in the causal rows, not in a module**: they carry the box of the aircraft track that is
  longest *so far* (batch: longest of the whole video), so an aircraft that taxied past earlier delays the hand-over of the
  arriving one. Live on `MwCSLbQ7QvXQ`: 223 frames (28 s) late, T_arr identical, the lead-marshaller report shifted. Replayed
  over the test set from the first-run rows (`scripts/rt_main_aircraft_delay.py`, reproduces the 223 frames exactly): the
  arrival window is identical to batch on 69 of 90 videos, under half identical on 16, and on 13 the arriving aircraft is
  handed over only after the batch T_arr. The test-set passes read the batch rows and cannot see this. Measured live on a
  second event with a predicted late hand-over (`ICfrXaND7Jqf`, rows written): **live T_arr 3764 against batch 4020, 32 s
  early**, declared from an earlier track at the edge of the frame; T_dep identical; the three belt-loader modules run there
  kept verdict and report, because they do not anchor on T_arr.
- **Second sizing sample** (`MwCSLbQ7QvXQ`, 20 modules, real-time speed): keeps up over the event, frame path 59.1 ms, but
  single frames stalled for up to 15 s around the arrival with the process tree at 23.2 GB on a 27 GB machine with a desktop
  session. Nothing is dropped and the verdicts are unaffected; every output is late by that much during the stall.
- **Quality**: the real-time inputs change 7 of 858 task verdicts against the production inputs (accuracy 86.7 % vs 86.6 %;
  the monthly CI output 88.1 %, the gap is the module build on this machine); scoped rows change 0 of 740.
- **Against post-processing**: the work per frame is not higher (the modules are about 4× cheaper live than as post jobs,
  which each parse the files and decode the video again); what real time pays for is holding the GPU for the length of the
  event: 1.25–1.8× the GPU time of back-to-back processing for a single module; for the full set the GPU is a quarter busy
  and the host is sized by cores and RAM; no spot capacity, and a faster card than the production T4.

## What the campaign fixed on the way (already committed)

- The declarations were generated from the default branches, while the test set runs other checkouts; `pf/rt/declarations.json`
  corrects 26 modules (cargo-doors reads belt loader tracks).
- A module that guards its per-frame block with `if len(det)` went silent when its scoped rows were empty: the subscription
  now leaves one presence row.
- Live tracker records take the same JSON trip as the batch file (three modules edit a box in place and crashed on tuples).

## Decision needed

1. **Interim verdicts for the three session-end modules** (safety-vests, gse-chocks, handrails-on-gse): without them they run
   live but say nothing until the camera stops. Vests and handrails are in PF-Q2-12; gse-chocks has no task.
2. **Sizing of a real-time host**: with every ready module in one session the bound is CPU and RAM (process per module, torch
   thread pools), not the GPU: one stream with 20 modules = about 8 cores, 18 GB RAM, 8 GB GPU memory, a quarter of an
   RTX 5070 Ti. Input for the Azure sizing (Maksym): a GPU host for real time needs the cores and the RAM of several
   post-processing jobs (3.3 vCPU / 8 GiB each today) per stream.

3. **A slow reader holds the frame path**: the pixel hand-off waits for every reader (a 16-slot frame ring), so one module
   that stalls delays every other output. Deeper per-module buffering or a drop policy per component is a PF-Q2-13 item.

4. **The causal rule for the main aircraft (PF-Q2-02)**: "longest so far" puts the live T_arr at risk on about one event in
   six. A rule that lets go of a track after 2 s without a box brings the replay to 74 of 90 identical arrival windows and 2
   late hand-overs, at the price of more passing aircraft reaching the tracker. It needs a choice and a live validation on
   the affected events (videos have to be fetched again: 6 are on disk).
