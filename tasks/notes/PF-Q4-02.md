# PF-Q4-02 · Lightening GM v2 and Tracker v2 for the real-time worker, and what it does to the verdicts

- **Owner:** Valentyn (+ Yurii) · **Agent:** gm-tracker-engineer · **Status:** in progress (pulled forward from Q4 on 2026-10-01)
- **Deps:** PF-Q2-02 (the branch), the realtime-pipeline worker (`external/realtime-pipeline`, main @ 7f10615)
- **Related:** `docs/analysis/rt_optimisation_plan.md` (the lever list), `docs/analysis/realtime_pipeline_alignment.md`

## The question

The worker (`gitlab.com/dxgat/detectors/realtime-pipeline`) does not keep up with real time on its resources. Lighten the
shared layer — our GM v2 and tracker v2, vendored there verbatim — and measure what the lightening does to the
post-processing verdicts.

## What "its resources" are (k8s/chunk-once.yaml @ 7f10615)

| container | CPU request | memory | GPU | runs |
|---|---|---|---|---|
| ingest | 100m | 6 Gi | — | 1-minute chunks from the bucket, decode |
| stage-detector | 100m | 4 Gi | — (dummy today) | gm head + plane track + camera / type / entity |
| general-model | **1** | 4–14 Gi | 1 (time-sliced) | chocks + vehicle heads, obstacle labelling |
| trackers | **1** | 8 Gi | 1 (time-sliced) | person + belt loader + GSE (plane copied) |
| modules | 100m | 1–4 Gi | — (dummy today) | verdicts |

Images are `python:3.11-slim` + pip `onnxruntime-gpu` / `torch` / `ultralytics`: CUDA EP only, no TensorRT. A chunk is one
minute (450–460 frames), so a container keeps up when it spends **≤ 130 ms per frame** on its own stretch of the chain.
The hand-off between containers is JSON with a base64 JPEG per frame (≈4 ms to decode per consumer on this machine,
≈7 ms on a pod core).

## Baseline: the tracker alone, busy stretch of zHxIAF2vUGxJ (frames 6961–8160), this machine

`scripts/with_cores.py N scripts/tracker_v2_run.py … --exact-fast` — one process pinned to N cores of a 4.7 GHz Ryzen,
RTX 5070 Ti otherwise idle. A pod core is roughly 0.6 of one of these; the T4 is slower on the networks.

| run | cores | classes | switches | ms per frame |
|---|---|---|---|---|
| base8 | 8 | all four | — | 37.8 |
| base1 | 1 | all four | — | 58.9 |
| worker8 | 8 | person, BL, GSE | — | 39.7 |
| worker1 | 1 | person, BL, GSE | — | **59.7** |
| worker1_sigma10 | 1 | person, BL, GSE | noise estimate every 10 s instead of 2 | 48.8 |
| worker1_fastsigma | 1 | person, BL, GSE | noise estimate on a half-resolution frame | 52.3 |
| worker1_reideval | 1 | person, BL, GSE | transport re-id BatchNorm in eval mode | 51.2 |

| worker1_reidhalf | 1 | person, BL, GSE | transport re-id in fp16 | 59.6 (no gain) |
| worker1_cudnn | 1 | person, BL, GSE | cuDNN autotuning | **164.3** (autotunes every new shape) |
| worker1_nothreads | 1 | person, BL, GSE | DeepSORT updates sequential (EXACT) | **47.5** |
| worker1_cv1 | 1 | person, BL, GSE | OpenCV / torch pools capped at 1 (EXACT) | 48.2 |
| worker1_set (twice) | 1 | person, BL, GSE | re-id eval + noise 10 s + sequential + pools capped | 45.1 / 47.9 |
| worker2_set | 2 | person, BL, GSE | the same set | **37.7** |
| worker8_set | 8 | person, BL, GSE | the same set | 31.8 (baseline 39.7) |

Reading: on one core the gain is in the EXACT switches — the thread pool of the three DeepSORT updates only fights the
GIL there (59.7 → 47.5 ms); the two not-exact switches add about 2 ms more on one core and about 8 ms on eight. The rest
is intrinsic: optical flow 10–12 ms, the per-object state machines 7, the masks 6, the two re-id forwards 11 — further
lightening means semantic changes (flow at lower resolution or fewer points, masks at a lower cadence).

Translated to the pod (core ≈ 0.6 of one here, networks 2–3× slower on the T4, JPEG decode ≈ 7 ms per frame per
container): one vCPU with the set ≈ 105–110 ms per frame — at the edge of the 130 ms a one-minute chunk allows; two vCPU
≈ 90 ms — keeps up. **The trackers container needs a CPU request of 2 and the switches; nothing else in it is cheap.**

So on the worker's one vCPU the tracker costs about 60 ms per frame here — about 100 ms on a pod core before the JPEG
decode and before the T4's slower networks: it does not keep up, which is what the worker shows.

Where the time goes (component timers; the three DeepSORT updates run in threads, so their times overlap): the transport
re-id — `torchvision.models.resnet34(pretrained=True)` in training mode, one forward per tracker per frame — 15–25 ms of
thread time; PyrLK optical flow 11–14 ms (CPU); the per-object state machines 7–9 ms (CPU); YOLO-seg masks 4–7 ms; the
full-frame noise estimate 2–4 ms (CPU, every 2 s).

`scripts/reid_bench.py`: the ResNet-34 forward itself is ~3 ms per call at these crop sizes whatever the mode or precision
(launch-bound; fp16 does not help), and in training mode the feature of a crop depends on which other crops share the
batch (max abs diff 7.3 in logit units; 3e-4 in eval mode) — production features are batch-composition dependent.

## Switches added (`pf/tracker/stream.py` TrackerOptions, `pf/tracker/reid.py`)

| switch | class | what it changes |
|---|---|---|
| `estimate_sigma_interval_s` | NOT exact | how often the full-frame noise estimate runs (production 2 s) |
| `reid_eval` | NOT exact | transport re-id BatchNorm on running statistics instead of the batch's |
| `reid_half` | NEAR | transport re-id in fp16 |
| `cudnn_benchmark` | NEAR | cuDNN autotuning (process-wide) — **do not use**: 164 ms per frame instead of 60, the autotuning re-runs for every new crop-batch shape, and the shapes change every frame |
| `reid_half` | NEAR | **no gain** (59.6 ms): the forward is launch-bound at these crop sizes |
| `deepsort_parallel=False` | EXACT | the three DeepSORT updates sequentially (no GIL contention on one core) |
| `cpu_threads` | EXACT | cap the OpenCV / torch CPU thread pools to the container's cores |
| `classes` | gated | only the classes the modules read (the worker tracks person, BL, GSE and copies the plane) |

Exposed in `scripts/tracker_v2_run.py` (flags), in the live pipeline (`rt_pipeline_run.py --tracker-opts k=v,…`,
`rt_resource_fit.py --tracker-opts`), and gated over the test set by `scripts/testset/variant_run.py`.

## Gate

`scripts/testset/variant_run.py --variant light --tracker-args "…"`: tracker v2 with the switches on the 21 videos on
disk (all four classes, so the modules get the airplane records they read), the modules on those rows, verdicts compared
pairwise with the v2 run set (`compare.py --baseline-root`). The result goes here when it has run.

## The worker's GM container through TensorRT (proposed patch for `realtime-pipeline`, push by Maksym)

The vendored `general_model/onnx_detector.py` already carries `tensorrt_provider(cache_dir)` (it is our file). What the worker
lacks is the provider selection and the libraries:

1. `general_model/load.py`: accept `GM_PROVIDER=tensorrt` — build each head with `provider="tensorrt"` and
   `trt_cache_dir=/cache/trt` (`YoloV8OnnxConfig` has both fields); keep `cuda` as the default until the verdict gate is green.
2. `general_model/Dockerfile`: `pip install onnxruntime-gpu tensorrt-cu12-libs` (the pod driver is CUDA 12; this machine runs
   the cu13 variant 10.16 with onnxruntime-gpu 1.29) and `LD_LIBRARY_PATH` extended with `site-packages/tensorrt_libs`.
3. `k8s/chunk-once.yaml`: a volume for the engine cache (an `emptyDir` is enough per pod life; a PVC avoids the rebuild at
   every start — the first build of the three fp16 engines takes minutes on a T4).

Measured here: three heads 19.2 → 11.1 ms busy; on the emulated T4 the ten pixel-free modules go from 144 ms per frame
(does not keep up) to 115 ms at the pessimistic end (`rt_optimisation_plan.md`). Parity so far: tolerant row parity only;
the module-verdict gate is `scripts/testset/variant_run.py --variant trt --gm-provider tensorrt`.
