## 2. General Model: формат запису і інвентар class_id

Рядок: `[x1, y1, x2, y2, conf, class_id]`, завжди довжина 6 (6 756 839 рядків, 0 інших довжин). Типи:
`[float, float, float, float, float, int]` — 6 553 040 рядків; `[float, float, float, float, **int**, int]` — 203 799 (усі класу 2, §5).

- Координати — абсолютні пікселі, обрізані до `[0..1920]×[0..1080]` (min 0.0, max 1920.0/1080.0; 0 записів поза кадром);
  завжди `x2 > x1`, `y2 > y1`. Цілочисельні float (`255.0`) у **всіх** класах, крім класу 2 у 3 відео (§5).
- `conf` ∈ [0,1] для всіх класів, крім 2; **100 % значень точно представимі у float16** (напр. `0.83349609375`) — вихід
  fp16-рушія, репр float64 (`gm_current.md` §2).
- Детекції на кадр: середнє 19,2–23,6, p90 26–33, максимум 38–53 (OKK5AlUiZnACMm кадр 52746). Рядок 930–1150 Б, макс 2 553 Б.
- **Порядок у кадрі** — не один сортований список, а конкатенація груп (див. `main.py:767-871`): (1) GM-детектор,
  `conf` за спаданням, поріг 0.35 (класи 0–24, min 0.350341796875); (2) chocks-модель → клас 25, поріг 0.10 (min 0.10015869);

## 4. Події літака (якорі T_arr / T_dep) — те, що stage detector має відтворити

Спостережена машина станів (усі 7 відео, значення в `state_at_set` у JSON):
`stopping` → `stopped` при `_static_frames` = 24 (`_stopping_time_thres`, 3 с); `stopping` → `moving` при `_moving_frames` = 9
(> 8); `stopped` → `proceeding` при `_moving_frames` = 6 (> 5); `proceeding` → `moving` при 17 (> 16); `proceeding` → `stopped`
при `_static_frames` = 1 (звідси «тріпотіння» proceeding↔stopped по 1–7 кадрів, до 56 переходів статусу на відео).
- **`arrival_frame`** пишеться **у кадрі початку `stopping`** (`_static_frames` = 1) і далі не змінюється — але не на першому
  `stopping`: у DjwtQRdZyt0sSk дві попередні зупинки (3466, 3514) без arrival, у EjMS44IMRSHs4i (4972) і OKK5AlUiZnACMm (4892)
  по одній. У всіх 7 відео arrival = початок **першого епізоду `stopping`, який доходить до `stopped`**; критерій, який трекер
  застосовує причинно (стоп-точка/ROI/лічильники не пояснюють — див. `ndjson_observed.json`), лишається невідомим без `cv_common`.
  Практично: причинний детектор може підтвердити T_arr лише через 24 кадри (3 с) — значення збігатиметься, доступність — із затримкою.
- **`have_arrival_stage`** → true на 25-му поспіль кадрі зі `_status = moving` до прильоту (3 відео); у 4 літак з'явився вже
  на стоянці — прапор назавжди false. **`have_pre_arrival_stage`** → true, коли `_stopped_counter` = 33 (≈4,1 с після
  `stopped`; це і є «зупинка 4 с» глосарію), після чого `_moving_counter` скидається в 0.

  не змінюється; після нього `_stops_count` скидається, наступні зупинки arrival не змінюють.

## 5. Аномалії та пастки

1. **Рядок класу 2**: 5-те поле — `int(mode(висота bbox/10)·10)` (580–680), не ймовірність (`main.py:854`); завжди останній у
   кадрі; у 3 відео координати **нецілі** (EjMS44IMRSHs4i 40 487 з 40 585 рядків, OKK5AlUiZnACMm 33 670 з 44 144, xMFpSi7ZM6pQFa
   14 782 з 30 049; напр. `[130.5, 138.78125, 1745.1875, 974.46875, 610, 2]`) — `BboxStabilizer` на «важкому» шумі; трекер
   пише ті самі бокси як int (`xyxy`, `_xyxy`), тому там IoU 0.99–1 замість точного збігу.
2. Рядки 29/30 — копії боксів транспорту з `conf` останньої детекції кадру (min 0.105 < поріг GM 0.35).
3. `conf` у конверті трекера завжди 0.0; `person` без стану (`state_dict: {}`), клас видно лише з `cls_str`.
4. Envelope-ключ `arrival_frame` у 61–63 об'єкт-кадрах літака після прильоту (у iE9pRtOwlwj9XY розтягнуто на 1653–12006 через
   розріджену присутність) — витік поля стану в конверт; модулі його не мають читати.
5. `tr_id` ≠ `_obj_id` і колізії `tr_id` між класами (§3) — ідентичність для паритету треба брати як `(cls_str, _obj_id)`
   для класів зі станом і `(cls_str, tr_id)` для person.
6. `_bl_type_*` **не витікає** в літак у жодному з 7 відео (`check_class_leakage` = 0), але схема має 39 ключів (`_height_mode`)
   проти 38/40, відомих стенду; версійності у файлах немає (X3). `data.bl_type` — лише `front`/`undefined`.
7. `_is_stopped` буває `null` (1–10 % кадрів), `_prev_status`/`to_status` змінюють форму у поодиноких кадрах BL
   (`unobserved`), `_p0` буває `null` при `to_numpy = []`.
8. Порожні кадри GM: 0–4 925 на відео (DjwtQRdZyt0sSk 3 420, EjMS44IMRSHs4i 4 925, OKK5AlUiZnACMm 4 381, xMFpSi7ZM6pQFa 3 771) —
   довгі ділянки без жодної детекції, у trackers ще більше (554–8 571).

## 6. Що і з яким допуском порівнювати старий ↔ новий GM/Tracker

Принцип: спочатку **польовий** паритет (по `frame_id`, не по позиції), потім **байтовий** (`json.dumps` рядка) — лише для
v1-compat-адаптера, який відтворює легасі-файл (`gm_current.md` §10.3). Умови X4: один декодер з обох боків, повний turnaround,
однакові ваги/пороги (0.35/0.10/0.40), прогрітий кеш, вільна машина.

| що | як порівнювати | допуск |
|---|---|---|
| нумерація | кількість рядків, ключі 1..N, `[]` на порожньому кадрі | точно (N = `nb_frames` того самого декодера) |
| GM-рядки класів 0–25, 31 | мультимножина `[x1,y1,x2,y2,cls]` на кадр + `conf` після зіставлення | координати точно (int-valued float, clamp 0..1920/1080); `conf` точно при тому самому fp16-рушії, інакше ≤ 1/2048 (1 ulp fp16); порядок груп (GM↓, chock↓, vehicle↓) — для байтового рівня |
| зведення по відео | кількість рядків на клас, min conf на клас, гістограма детекцій/кадр | кількість ±0,5 %, min conf точно (ловить зсув порогу/моделі), присутність усіх id 0–25, 29–31 |
| рядки класу 2 | множина кадрів присутності; бокс; 5-те поле | кадри точно; бокс точно там, де v1 цілий, ±1 px там, де стабілізатор (3 відео); 5-те поле — int-мода точно (потребує всього відео → тільки v1-compat пост-режим, у шині v2 замінити на справжній `conf`) |
| рядки 29/30 | множина боксів на кадр | бокси точно; `conf` не порівнювати (дефект), для байтового рівня — відтворити як є |
| tracker: об'єкти на кадр | зіставлення за `(cls_str, _obj_id)` (person — за `tr_id`) і IoU ≥ 0.9 | кількість об'єктів на кадр точно; distinct `_obj_id` на клас на відео ±0; літак рівно 1 (X1) |
| `state_dict` константи | усі поля «const» з §3 (пороги, ROI, `_init_dots_lifetime`, `_class_name`, `_init_xyxy`, `_height_mode`) | точно; набір і **порядок** ключів на клас точно (39/34/0) |
| `_status` | послідовність на кадр по об'єкту | збіг ≥ 99 % кадрів; кожен перехід ±1 кадр; кількість епізодів `stopping`/`stopped` точно |
| `arrival_frame`, `departure_frame`, `have_*` | значення та кадр встановлення | значення **точно** (це якорі stage detector); кадр встановлення точно у пакетному режимі, у причинному — ≤ +24 кадри для arrival, документована затримка |
| `_xyxy`, `_stop_point`, `_bl_type_bbox` | по об'єкту й кадру | IoU ≥ 0.99 або ±1 px; стоп-точка ±2 px; `_bl_type_frames` лічильники точно |
| лічильники (`_static_frames`, `_moving_frames`, `_moving_counter`, `_stopped_counter`, `_stops_count`) | по кадру | точно за умови однакової `_status`-послідовності |
| `_p0`, `_st`, `_segm_points`, `to_numpy` | не побайтово: довжина списку, частка `null`, `to_numpy` | довжина ±10 %, `null`-патерн ±1 % кадрів (залежать від OpenCV/SAM) |
| `data`, конверт | `data.bl_type` на кадр; набір і порядок ключів конверта; `conf` = 0.0 | точно; зайвий `arrival_frame` у конверті — відтворювати лише у v1-compat |
| розмір | середні байти на рядок | ±5 % (проксі на втрачені/додані поля) |
| байтовий рівень | `json.dumps(obj) + "\n"` == рядок v1 | 100 % рядків для v1-compat писаря; будь-яка різниця → спершу польовий діф |

Мінімальний набір даних для цього — ці 7 відео (усі мають T_arr, 3 мають T_dep, 3 — «фальшиві» зупинки, 3 — float-бокси
літака), далі — збалансована вибірка з fail-розміткою (`tools/pick_balanced.py`), бо парність тут показує лише «те саме, що v1».
