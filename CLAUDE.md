# Prime Flight (PF) — DXGAT real-time roadmap workspace

Це **керуючий воркспейс** ліда проєкту Prime Flight: уся документація, ролі агентів і беклог в одному місці.
Код живе в GitLab-репозиторіях `dxgat/*`; **свіжі read-only клони — у `external/` цього воркспейсу** (gitignored: 27 модулів,
`general_model`, `db_worker`; `cv_trackers`/`cv_common`/`camera_software` недоступні — PF-X-05). Стенд стрімінгу — `G:\gat-streaming\`.
Новий код збираємо в пакеті `pf/` цього репо (`pf/README.md`): контракт → приймач → GM v2 → Tracker v2 → stage detector → адаптери модулів.
Тут — контекст, рішення, задачі. Будь-який агент, що працює над PF, спочатку читає цей файл.

## Що за проєкт, одним абзацом

DXGAT (DeepX Ground Aircraft Turnaround) — CV-система, що з двох камер на гейті (cone + wing) перевіряє 27 чеклист-задач
безпеки обслуговування літака (chocks, cones, wing walkers, handrails, vests, pushback...). Сьогодні це **пост-обробка**:
CameraBox пише 1-хвилинні чанки → після події merge у full-turn відео → General Model (GM) → трекери → модулі → вердикти
Pass / Fail / Not observed → MongoDB → RampVision website. **Time to Result ≈ 24 год.**
Prime Flight — 12-місячний roadmap, що поступово переводить систему на дві гілки (real-time + пост) і доводить
Time to Result до **≈5–6 год для пост-частини** та **секунд для real-time-перевірок**.

## Головний KPI і квартали (деталі: @docs/06_roadmap.md)

| Квартал | Тема | Клієнт бачить | Time to Result* |
|---|---|---|---|
| Q1 (міс. 1–3) | Continuous upload + швидший post-processing (Wi-Fi/SIM чанки, stage detector, без раннього merge) | відео їде на сервер, поки CameraBox ще пише | ~24h → ~15h |
| Q2 (міс. 4–6) | Real-time architecture foundation (окрема RT-гілка, GM/Tracker під RT, перший модуль у RT) | перші перевірки дають результат до завершення merge | ↓ |
| Q3 (міс. 7–9) | Real-time expansion + alerting (більше модулів, бекенд-алерти) | важливі safety-івенти тригерять алерти | ↓ |
| Q4 (міс. 10–12) | Максимальне RT-покриття + оптимізація (GM/Tracker/stage detector, стрімінг гейтів на RampVision) | максимум практичних перевірок у RT | ~5–6h |

\* ілюстративні цілі, підлягають валідації замірами (baseline — задача PF-Q1-08).

## Незмінні правила (для всіх агентів)

**Архітектурні інваріанти стрімінгу** (виміряні, не думки; див. `docs/02_target_architecture.md`):
- X1. Один трекер на подію, ніколи не скидається (скидання раз на 7,5 с → 297 «літаків» замість 5).
- X2. `frame_id` абсолютний і явний; приймач заповнює дірки заглушками, а не пропускає кадри.
- X3. `schema_version` у кожному записі контракту.
- X4. Декодер закріплений з обох боків будь-якого порівняння (ffmpeg ≠ OpenCV на немонотонному DTS).
- Чанк — одиниця транспорту, не обробки. Модуль про чанки не знає.
- Якорі подій (T_arr, T_dep, BL@door, BL leave, pushback_attached) має **один власник — stage detector**, не копії в модулях.

**Семантика вердиктів**: Pass/Fail/Not observed/NO-with-obstacles визначено клієнтом у `docs/05_module_logic.md`.
Перенос у RT не змінює семантику мовчки. Якщо тригер треба перевизначити (S1-перевірки) — це окрема задача з позначкою
`trigger-change` і погодженням з Ігорем/Оксаною.

**Вимірювання**: «технічна готовність ≠ користь». Модуль не вважається доставленим у стрімінг без заміру на fail-відео
(приклад: pushback-pathway — повнота 0 з 4 при 85 % «точності»). Парне порівняння пакет↔стрім валідне завжди,
абсолютна точність — лише там, де є fail-розмітка (Main gear chocks).

**Git / репозиторії**:
- Робочі репо DeepX: **без** трейлерів `Co-Authored-By: Claude` у комітах. Коміти — короткі, англійською, у стилі репо.
- `git push`, створення MR — робить людина. Агент готує гілку, коміт, опис MR у `tasks/` або у відповіді.
- Не міняти запінені версії `cv_common` у модулях без окремої задачі (10 різних пінів — відомий борг, PF-Q3-05).
- Прод-інференси (500–800 МБ на відео) і ваги в git не кладемо; ваги — DVC, дані — бакети (`docs/08_repos.md`).

**Мова**: документи й обговорення — українською, код/коміти/технічні терміни — англійською.

```

2. Знайди свою задачу за ID (PF-Qn-nn), перевір owner/agent/deps/acceptance.
3. Працюй у своїй зоні (див. картку агента). Прод-код читай у `external/<repo>` (read-only), стенд у G:\gat-streaming; новий код — у `pf/`.
   Звіти аналізу — `docs/analysis/` (індекс у `docs/analysis/README.md`).
4. Результат: код у гілці + нотатка у tasks/notes/<ID>.md (що зроблено, як перевірено, що лишилось) + оновлений статус у BOARD.md.
5. Все, що змінює контракт кадру, stage-події або клієнтську логіку — окремим пунктом «Decision needed» у нотатці.
```
